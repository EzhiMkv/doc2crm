# doc2crm — архитектура (набросок v0.1)

> **Суть одним предложением:** агент, который превращает фото или PDF счёта/акта
> в оформленную сделку в Битрикс24 — сам извлекает поля, находит контрагента,
> подбирает товары из каталога, а в спорных местах переспрашивает человека.

Демо полного цикла прикладной LLM-интеграции: извлечение документов, RAG по
документам, RAG по каталогу, агент с инструментами, MCP, human-in-the-loop.

---

## Три пользовательских сценария

| # | Сценарий | Что демонстрирует |
|---|----------|-------------------|
| 1 | **Документ → сделка.** Кидаешь в Telegram фото счёта — в Битриксе рождается сделка с контрагентом, товарами и комментарием в таймлайне. | Vision-LLM, structured output, валидация, human-in-the-loop, MCP-инструменты |
| 2 | **Спроси по документам.** «На какую сумму были счета от ООО Ромашка за март?» — ответ с цитатами источников. | RAG-пайплайн: чанкинг, эмбеддинги, векторный поиск, цитирование |
| 3 | **Подбор из каталога.** «Клиенту нужен насос для скважины 30 метров до 30к» — агент находит товары в каталоге Битрикса и прикладывает к сделке. | RAG для семантического поиска по каталогу, гибридный поиск, NL → фильтры |

## Компоненты

### 1. `apps/api` + `apps/bot` — интерфейс
Telegram-бот вместо веб-фронта в v1: загрузка фото с телефона из коробки,
ноль затрат на UI, идеальное демо. FastAPI принимает вебхук, раздаёт
SSE-стриминг ответов, `/metrics` через `prometheus-fastapi-instrumentator`.

### 2. `agent/` — оркестрация (LangGraph)
Граф с состоянием, узлы:

- **extract** — vision-LLM извлекает поля документа в Pydantic-схему
  (`InvoiceSchema`: продавец, ИНН, номер, дата, позиции, суммы)
- **validate** — контрольные суммы, форматы ИНН, дубликаты по номеру счёта;
  полю присваивается confidence
- **match** — поиск контрагента по ИНН/названию через MCP; не найден —
  вопрос пользователю «создать нового?»
- **confirm (HITL)** — граф **прерывается**, пользователю показывается
  итоговая карточка; подтверждение приходит асинхронно, состояние ждёт
  в checkpoint (Postgres). Порог уверенности полей — часть решения
- **execute** — создание сделки + товаров + комментария в таймлайн через MCP
- **report** — человекочитаемый отчёт в чат: что сделал, что исправил руками

**Почему LangGraph:** checkpointing (диалог живёт часами), нативное
прерывание графа для HITL, ретраи. Рассматривались OpenAI Agents SDK
(привязка к GPT, а нужна провайдер-агностичность под 152-ФЗ) и Pydantic AI
(отличный DX, но без durable execution из коробки). Старые цепочки
LangChain для оркестрации не используются — только LangGraph.

### 3. Интеграция с Битрикс24 — два уровня

> **Важно (сентябрь 2026):** у Битрикса24 появился **нативный MCP-сервер** —
> внешние AI-системы могут действовать в портале от имени сотрудников
> (настройки портала → MCP). Плюс dev-эндпоинт `mcp-dev.bitrix24.tech`,
> отдающий агентам документацию REST API. Это валидация рынка, но не замена
> нашему проекту: нативный MCP — обёртка над REST, без RAG, без извлечения
> документов, без наших бизнес-сценариев.

**Уровень 1 (v1, текущая неделя): собственный клиент `b24client`.**
Пайплайн говорит с Битриксом через тонкий асинхронный клиент:
throttling (лимит ~2 rps), batch до 50 операций, обработка
`QUERY_LIMIT_EXCEEDED` с backoff. Полный контроль над ретраями и лимитами —
демо не зависит от беты нативного MCP.

**Уровень 2 (v1.1): пакет `bitrix-mcp` — «умные инструменты».**
Генерик-обёртки над REST никому не нужны — их делает сам Битрикс.
Наш пакет выставляет только то, чего нет в нативном MCP:

| Инструмент | Что умного |
|---|---|
| `semantic_product_search` | RAG-поиск по каталогу (эмбеддинги, гибрид) |
| `find_duplicate_deal` | поиск дублей сделки по контрагенту/сумме/периоду |
| `match_counterparty` | матчинг контрагента по реквизитам с confidence |

Отдельно в демо: подключение **нативного** MCP Битрикса к Claude/Cursor —
скрин и абзац в README («работал и с нативным MCP вендора, и со своими
инструментами»).

### 4. `rag/` — два индекса, один механизм
- **Документы:** чанкинг по смысловым блокам (таблица позиций — отдельные чанки),
  в текст эмбеддинга добавляется мета (продавец, дата, номер)
- **Каталог:** карточка целиком; в текст эмбеддинга — название + описание +
  атрибуты (цена — только фильтром, не в векторе)
- **Эмбеддинги:** `multilingual-e5` локально или GigaChat embeddings —
  переключается одной переменной окружения
- **Поиск:** pgvector + гибрид (`tsvector` + вектор, слияние через RRF);
  NL → структурированные фильтры (цена, дата) через LLM до векторного поиска
- **Свежесть:** переиндексация при загрузке документа, каталог — по крону
- **Качество:** цитаты источников в каждом ответе, recall@10 на мини-наборе запросов

### 5. `providers/` — LLM-слой
OpenAI-совместимый протокол покрывает: DeepSeek, GigaChat, YandexGPT,
self-hosted vLLM + Qwen. Провайдер = переменная окружения. В коде —
тонкие обёртки без тяжёлых абстракций (уроки критики LangChain 2023–24).

### 6. `evals/` — метрики качества
- **Extraction:** golden set 20–30 документов, точность по полям
  (ИНН/суммы отдельно — там чаще всего галлюцинации), стоимость одного документа
- **RAG:** recall@10 на 20 размеченных запросах
- Отчёт: таблица в README, обновляется скриптом `make eval`
